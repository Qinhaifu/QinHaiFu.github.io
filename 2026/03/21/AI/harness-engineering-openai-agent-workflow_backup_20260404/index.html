OpenAI Harness Engineering：人类指导，Agent 执行

Created2026-03-21|Updated2026-03-21|AI工程
|Post Views:

原文链接：Harness Engineering — OpenAI

最近读到 OpenAI 工程团队发布的一篇文章，介绍了他们如何在内部工程实践中大规模使用 AI Agent（Codex）进行软件开发。文章视角非常实际，涵盖了从理念转变到工具链建设的方方面面，读完之后收获颇多，整理如下。

1. 核心理念：人类指导，Agent 执行

OpenAI 工程团队的核心工作模式可以用一句话概括：

**Humans steer. Agents execute.**（人类指导，Agent 执行。）

在这套模式下，代码几乎完全由 Agent（Codex）负责编写，人类工程师不再亲自敲代码，而是专注于描述任务、验证结果、提供反馈。

这种转变带来了一种截然不同的工程工作模式——专注于系统、脚手架和杠杆作用，而非具体的代码实现。

2. 工程师角色的重新定义

当 Agent 负责写代码之后，工程师的工作并没有消失，而是被提升到了更高的层次：

  • **不再”再试一次”**：当某个任务失败时，修复方式几乎从不是”让 Agent 再试一次”。
  • 聚焦能力缺口：工程师会介入失败的任务，思考”缺少了什么能力？如何让 Agent 既能理解又能执行这项能力？“
  • 通过 Prompt 与系统交互：工程师描述任务 → 运行 Agent → Agent 开启 Pull Request → 循环迭代直到通过所有审查者（包括 Agent 审查者和人类审查者）。

这是一种”Ralph Wiggum Loop“式的工作流：Agent 在本地和云端反复审查自己的变更、响应反馈、持续迭代，直到满足所有条件才完成一个 PR。

3. 提高应用可读性（Legibility）

随着代码吞吐量提升，人工 QA 成为瓶颈。解决方案是让 Agent 自己验证代码质量：

  • 通过 LogQL 获取日志
  • 通过 PromQL 查询性能指标
  • 通过 TraceQL 获取链路追踪数据

让 Agent 能够主动感知应用状态，从而自主验证所生成的代码是否满足预期行为。

4. 仓库即知识系统

OpenAI 团队将代码仓库本身作为 Agent 的知识来源与工作系统。然而，他们总结出了”文档作为知识载体”的四大痛点：

问题 说明
上下文是稀缺资源 Agent 的上下文窗口有限，信息必须精简
太多指导等于没有指导 信息过载让 Agent 无法区分重要与次要
文档会”腐烂” 人类不及时维护，文档很快与代码现实脱节
难以验证 大量文档难以确认是否仍然准确

解决方案：设计渐进式信息呈现（Progressive Disclosure）的文档目录索引，让 Agent 按需加载知识，而非一次性塞满上下文。

5. Agent 可读性是首要目标

当 Agent 承担的工作越来越多，甚至接管整个代码仓库时，人类工程师的首要目标变成了：

让代码仓库对 Agent 更友好、更易读、更易操作。

关键原则：

  • 任何无法在上下文中被访问的信息，都等于不存在。
  • 持续将上下文信息沉淀到仓库中，为 Agent 提供完整的项目知识。
  • 让 Agent 能够直接检查、验证、修改相关信息。

6. 架构约束与”品味”执行

仅靠文档无法保证 Agent 生成的代码风格连贯。OpenAI 的做法是：

  • 宏观把控，不微观限制：设定严格的边界（边界内可以自由发挥），但不规定具体的实现方式。
  • Agent 在边界严格、结构可预测的环境中表现最好。
  • 通过自定义代码检查器强制执行规范，例如：
    • 结构化日志格式
    • 模式与类型的命名约定
    • 文件大小限制
    • 平台特定的可靠性要求
  • 检查器的错误信息本身就是给 Agent 的修复指令，直接注入到 Agent 上下文中。

7. 吞吐量改变了 PR 哲学

高吞吐量的 Agent 开发模式，彻底改变了对 Pull Request 的态度：

传统人工开发 Agent 开发
倾向大 PR，积累后再合并 拆小 PR，尽快合并
Review 周期长，阻塞少 Review 快，不因 Review 阻塞 Agent 效率
修复代价高，谨慎提交 出问题让 Agent 快速修复，不惧小错误

8. “Agent 生成”意味着什么

在 OpenAI 内部，Agent 生成的内容已经不仅仅是业务代码，而是延伸到了工程链路的每个环节：

  1. 产品代码与测试（Product code and tests）
  2. CI 配置与发布工具（CI configuration and release tooling）
  3. 内部开发者工具（Internal developer tools）
  4. 文档与设计历史（Documentation and design history）
  5. 评估工具链（Evaluation harnesses）
  6. 审查意见与回复记录（Review comments and responses）
  7. 管理代码库本身的脚本（Scripts that manage the repository）
  8. 生产环境仪表板定义文件（Production dashboard definition files）

人类工程师仍然在生产循环中，但不负责具体执行，而是专注于更高层次的工作：方案设计、架构设计、环境搭建。

9. 自主性水平的提升

给定单个 Prompt，Agent 现在已经可以完成以下全套流程：

  1. 验证代码仓库当前状态
  2. 复现上报的 Bug
  3. 录制演示失败的视频
  4. 实现修复
  5. 驱动应用验证修复效果
  6. 录制演示修复结果的视频
  7. 开启 Pull Request
  8. 响应 Agent 和人类的反馈
  9. 检测并修复构建失败
  10. 仅在需要判断时才升级给人类
  11. 合并变更

10. 熵与垃圾回收

完全自主的 Agent 也引入了新问题：

Codex 会复制仓库中已有的模式——即便是那些不平衡或不够理想的模式。随着时间推移，这会导致不可避免的代码漂移。

仓库中原有的”垃圾代码”会成为 Agent 的错误参照，产生更多”垃圾”。解决方案：

  • 辅助函数集中化：优先使用共享工具包，而非各处手写 helper，保持不变量集中。
  • 边界校验：不做”YOLO 式”数据探测，依赖类型化 SDK，防止 Agent 基于猜测的数据结构构建逻辑。
  • 定期垃圾回收：设定一批后台 Codex 任务，定期扫描偏差、更新代码质量评分、开启针对性的重构 PR。大多数重构 PR 可以在一分钟内完成审查并自动合并。

11. 我的思考

读完这篇文章，我认为为 Agent 搭建基础设施包含以下几个关键部分：

  1. 项目工程品味规范：明确的架构约束与代码风格规范，通过自动化检查器强制执行
  2. 项目各个系统规范：让 Agent 能够理解和访问各系统的接口与行为
  3. 质量保障系统：自动化测试、日志、指标，让 Agent 具备自我验证能力
  4. Agent 工作流程：清晰的任务分解、PR 粒度控制、反馈循环设计

这套体系最打动我的一点是：它不是在让人类适应 AI，而是在让整个工程环境变得对 AI 更友好。这或许才是未来软件工程的核心竞争力所在。
