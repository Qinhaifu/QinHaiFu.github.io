Anthropic《Harness Design for Long-Running Application Development》读后感：长任务 Agent 的 Harness 设计方法

Created2026-04-05|Updated2026-04-05|AI工程
|Post Views:

原文：https://www.anthropic.com/engineering/harness-design-long-running-apps
作者：Prithvi Rajasekaran（Anthropic Labs）
发布时间：2026-03-24
阅读时间：2026-03-30

一、背景：为什么长时间 Agent 开发不能只靠“单次直出”

这篇文章最打动我的点是：它没有神化模型能力，而是把问题摊开讲清楚——当任务跨度从 20 分钟拉到 2~4 小时后，朴素链路（一个 Agent 从头写到尾）会稳定出现失败模式。

核心有两个：

1、上下文焦虑（Context Anxiety）

（1）随着 context window 逐步填满，模型连贯性会下降。
（2）有些模型在接近上下文上限时会“提前收尾”，看起来像完成了，实际是草草结束。
（3）典型应对是 Context Reset：不是做摘要压缩（Compaction），而是给新 Agent 一个全新上下文，再通过 handoff artifact 接棒。

作者给的实测结论也很关键：Claude Sonnet 4.5 对上下文焦虑更敏感，而 Opus 4.6 已经明显改善，Reset 的必要性下降。

2、自我评价偏差（Self-Evaluation Bias）

（1）让 Generator 自评，常见结果是“过于乐观”，甚至会给中等质量打高分。
（2）主观任务（例如设计）问题更明显，因为缺少二进制通过/失败信号。
（3）更有效的解法是“生成与评估分离”：独立 Evaluator 做评分和验收，比逼 Generator 自我批判更稳。

一句话先立住：Harness 的起点不是“多加组件”，而是承认模型在长链路上确实有能力边界。

二、方案与过程：GAN 启发的生成-评估循环，以及两组实验

1、总体架构：Planner → Generator ↔ Evaluator

作者借鉴了 GAN 的对抗迭代思路，抽成了下面这个流程：

你可以理解为：Planner 管“做什么”，Generator 管“怎么做”，Evaluator 管“做得是否达标”。三者分工后，系统才有机会在长时间运行下保持质量。

2、实验一：前端设计质量提升（把主观审美变成可评分）

问题很真实：模型默认会产出“能用但普通”的页面，工整但没灵魂。

他们做的关键动作，是把“审美”拆成可以执行的评分标准，并同时给 Generator 和 Evaluator 使用：

维度 说明 默认表现
设计质量 是否有整体气质，而不是拼装感 偏低
原创性 是否有明确创意决策，避免“AI 套路味” 偏低
工艺 字体层级、留白节奏、色彩和谐、对比度 较好
功能性 用户能否顺畅完成任务 较好

他们特别提高了“设计质量 + 原创性”的权重，并显式惩罚常见 AI 模式（例如白卡片+紫渐变这类模板感）。

实现细节上：

（1）基于 Claude Agent SDK 实现循环。
（2）Evaluator 用 Playwright MCP 直接操作运行中的页面（不是只看截图）。
（3）一次完整运行做 5~15 轮迭代，最长可到 4 小时。
（4）用 few-shot + 评分分解去校准评估器尺度。

最有代表性的案例是博物馆网站：前 1~9 轮都在“精致常规”范围内，第 10 轮突然跃迁到 3D 空间叙事（棋盘地面、墙面画作、走廊导航）。这种创意跳变，单次生成几乎很难碰到。

这里有个很值得记笔记的结论：评价标准的措辞会反向塑造生成方向。比如“博物馆级别设计”这类语言，会把模型往特定风格持续拉拢。

3、实验二：全栈长时编码（从 Sprint 化到简化 Harness）

3.1 初版三 Agent 分工

Planner：从 1~4 句需求生成高层规格，强调“交付目标”，避免过早绑定技术细节。
Generator：按 Sprint 实现（React + Vite + FastAPI + SQLite，后续升级 PostgreSQL），每个 Sprint 后自评再交 QA。
Evaluator：用 Playwright MCP 走真实用户路径，检查 UI / API / DB，并按硬门槛判定是否过关。

另外还有 Sprint Contract：每个 Sprint 开始前，Generator 和 Evaluator 先协商“完成定义”，通过文件互相对齐预期。

3.2 对比结果：质量和成本直接拉开

方式 时长 费用 质量
Solo（单 Agent） 20 分钟 $9 核心功能损坏，逻辑断线
Full Harness 6 小时 $200 可玩、功能完整、视觉一致，含 AI 能力

结论很直白：Harness 显著更贵（20x+），但质量上是“能不能交付”的差距，不只是“好一点”。

3.3 Evaluator 不是“开箱即用”，必须调优

作者明确提到：默认模型做 QA 往往偏宽松。发现问题后，容易自己把问题合理化（“好像也还行”）。

有效做法是：

（1）读评估日志。
（2）对照人工判断找偏差。
（3）回改 QA Prompt。
（4）重复迭代。

这个过程本质上是“训练评审标准”，不是简单换个提示词一把梭。

4、Harness 迭代：把组件当假设，而不是圣经

作者引用《Building Effective Agents》的原则我很认同：先做最简单可行方案，确有必要再加复杂度。

为什么这么说？因为每个组件背后都在编码一个假设：

（1）加 Planner：假设模型拿短需求会漏范围。
（2）加 Sprint：假设长链路实现会跑偏。
（3）加 Evaluator：假设自评会偏乐观。
（4）加 Context Reset：假设超长上下文会失稳。

那么问题来了，既然是“假设”，就不能一劳永逸。模型能力一变，旧假设可能就过时。

对应到工程落地，我理解有 4 条实操原则：

（1）把组件当可验证假设，持续做 A/B 或日志复盘。
（2）定期做减法，优先移除“曾经必要、现在累赘”的脚手架。
（3）按任务难度动态开关组件，不搞一刀切。
（4）围绕真实失败样本迭代（漏测、跑偏、提前收尾），最小增量加组件。

5、Opus 4.6 后的结构变化：移除 Sprint

旧版需要 Sprint，是因为早期模型长时稳定性不足；新版（Opus 4.6）在规划、长跑、自检上明显更强，原先必须“分段纠偏”的必要性降低。

结构从：

（1）旧：每个 Sprint 后都评估。
（2）新：Generator 先完整构建，再统一 QA（必要时再下一轮 build + QA）。

这也带来一个关键判断：Evaluator 价值并非恒定，而是边界条件相关。

（1）任务在模型能力范围内时，Evaluator 可能主要增加时延和成本。
（2）任务在能力边缘时，Evaluator 往往是“最后一公里”质量保障。

他们在浏览器 DAW 项目上的新版数据如下：

阶段 时长 费用
Planner 4.7 分钟 $0.46
Build Round 1 2 小时 7 分钟 $71.08
QA Round 1 8.8 分钟 $3.24
Build Round 2 1 小时 2 分钟 $36.89
QA Round 2 6.8 分钟 $3.09
Build Round 3 10.9 分钟 $5.88
QA Round 3 9.6 分钟 $4.06
合计 3 小时 50 分钟 $124.70

产出是一个可运行的浏览器 DAW（Arrangement View、Mixer、Transport 完整），并且能通过内置 Claude Agent 做自然语言编曲控制。

三、总结：Harness 本质是“能力边界管理系统”

这篇文章给我的核心启发，不是“多 Agent 更高级”，而是下面这 5 句：

（1）生成与评估分离，是对抗自评偏差的最强杠杆之一。
（2）评估标准不只是验收工具，它会反向塑造生成行为。
（3）Evaluator 必须调优，默认尺度通常不够苛刻。
（4）每次模型升级，都要重评 Harness 组件是否还必要。
（5）Harness 复杂度不会消失，只会随着模型能力和任务难度迁移。

如果要压成三句话的方法论主线：

（1）围绕当前模型能力边界搭脚手架。
（2）坚持最小必要复杂度，能不加就不加。
（3）持续重评估，敢于删旧组件，也敢于补新约束。

最后给一个工具链场景的 MVP（可直接落地）：

（1）最小角色先上 Generator + Evaluator。
（2）验收标准至少包含：可运行、测试通过、关键路径通过。
（3）简单改动（文案/样式/局部重构，且不动接口与数据结构）可以暂时关闭 Evaluator 降本提速。

四、个人思考

（1）Sprint Contract 很像软件工程里的“接口契约先行”，这个抽象非常实用。
（2）Evaluator 调优是持续工程，不是一次配置。
（3）“只有任务超出模型能力边界时，Evaluator 才值回票价”这个判断标准，可以直接拿去指导成本控制。
（4）在 3~4 小时和百美元量级里拿到可用 DAW，工程效率已经非常夸张。

如有理解偏差或笔误，欢迎交流讨论。
