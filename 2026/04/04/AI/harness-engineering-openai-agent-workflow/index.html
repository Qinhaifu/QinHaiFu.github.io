OpenAI《Harness Engineering》读后感：如何为Agent搭建友好的工程环境

Created2026-04-04|Updated2026-04-04|AI工程
|Post Views:

原文链接：Harness Engineering — OpenAI

最近读到 OpenAI 工程团队发布的《Harness Engineering》文章，介绍了他们如何在内部大规模使用 AI Agent（Codex）进行软件开发。读完之后，我感觉这不仅仅是一篇技术文章，更像是一份工程哲学宣言。

为什么这么说？因为文章讲的不是”怎么用AI写代码”，而是”怎么重构整个工程环境，让AI成为一等公民“。这个视角非常独特，也让我开始反思：我们现在的开发流程，真的为AI准备好了吗？

（你可以理解为，OpenAI不是简单地给工程师配了个”智能助手”，而是重新设计了整个工程体系，让AI能自主完成从需求到上线的全流程。）

作为一个在日常开发中深度使用 Claude Code、Cursor 等工具，并且尝试过搭建自定义 Agent 工作流的人，我意识到：单纯会用工具还不够，关键是要构建一个对AI友好的工程环境。下面我就结合OpenAI的实践和我自己的经验，聊聊这个话题。

一、OpenAI的Harness Engineering实践解析

1. 核心理念：Human steer, Agents execute（人类指导，Agent执行）

OpenAI 工程团队的工作模式可以用一句话概括：

Humans steer. Agents execute.

在这套模式下，代码几乎完全由 Agent 负责编写，人类工程师不再亲自敲代码，而是专注于：

  • 描述任务需求
  • 验证结果质量
  • 提供反馈指导

这种转变带来了一种截然不同的工程思维——专注于系统设计、脚手架搭建和杠杆作用，而不是具体的代码实现。

（这让我想起自己用 Claude Code 的经历：有时候我花在”描述清楚需求”上的时间，比直接写代码还多。但一旦描述清楚，AI能生成比我手写更规范的代码。）

2. 工程师角色的重新定义：从”码农”到”架构师+教练”

当 Agent 负责写代码之后，工程师的工作并没有消失，而是被提升到了更高的层次：

（1）**不再”再试一次”**：当某个任务失败时，修复方式几乎从不是”让 Agent 再试一次”。

（2）聚焦能力缺口：工程师会介入失败的任务，思考”缺少了什么能力？如何让 Agent 既能理解又能执行这项能力？“

（3）通过 Prompt 与系统交互：工程师描述任务 → 运行 Agent → Agent 开启 Pull Request → 循环迭代直到通过所有审查。

这是一种”Ralph Wiggum Loop“式的工作流：Agent 在本地和云端反复审查自己的变更、响应反馈、持续迭代，直到满足所有条件才完成一个 PR。

3. 提高应用可读性：让Agent具备自我验证能力

随着代码吞吐量提升，人工 QA 成为瓶颈。OpenAI 的解决方案是让 Agent 自己验证代码质量：

  • 通过 LogQL 获取日志（你可以理解为专门查询日志的查询语言）
  • 通过 PromQL 查询性能指标（Prometheus的查询语言）
  • 通过 TraceQL 获取链路追踪数据（分布式追踪查询）

让 Agent 能够主动感知应用状态，从而自主验证所生成的代码是否满足预期行为。

4. 仓库即知识系统：文档的四大痛点与解决方案

OpenAI 团队将代码仓库本身作为 Agent 的知识来源与工作系统。然而，他们总结出了”文档作为知识载体”的四大痛点：

问题 说明 我的理解
上下文是稀缺资源 Agent 的上下文窗口有限，信息必须精简 Claude的上下文也就几万个token，不可能塞进所有文档
太多指导等于没有指导 信息过载让 Agent 无法区分重要与次要 就像给人一堆未经整理的资料，反而找不到重点
文档会”腐烂” 人类不及时维护，文档很快与代码现实脱节 我们项目里的README，有几个能跟实际代码同步更新？
难以验证 大量文档难以确认是否仍然准确 怎么知道文档说的某个API还能用？

解决方案：设计渐进式信息呈现（Progressive Disclosure）的文档目录索引，让 Agent 按需加载知识，而非一次性塞满上下文。

5. Agent可读性是首要目标

当 Agent 承担的工作越来越多，甚至接管整个代码仓库时，人类工程师的首要目标变成了：

让代码仓库对 Agent 更友好、更易读、更易操作。

关键原则：

  • 任何无法在上下文中被访问的信息，都等于不存在。
  • 持续将上下文信息沉淀到仓库中，为 Agent 提供完整的项目知识。
  • 让 Agent 能够直接检查、验证、修改相关信息。

（这个原则点醒了我：我们经常在开会、聊天中传递重要信息，但这些信息对AI来说就是”不存在”的。必须沉淀到文档或代码注释中。）

6. 架构约束与”品味”执行：宏观把控，不微观限制

仅靠文档无法保证 Agent 生成的代码风格连贯。OpenAI 的做法是：

  • 设定严格的边界（边界内可以自由发挥），但不规定具体的实现方式。
  • Agent 在边界严格、结构可预测的环境中表现最好。

通过自定义代码检查器强制执行规范，例如：

  • 结构化日志格式
  • 模式与类型的命名约定
  • 文件大小限制
  • 平台特定的可靠性要求

检查器的错误信息本身就是给 Agent 的修复指令，直接注入到 Agent 上下文中。

（这让我想起在团队中推广代码规范的经验：单纯靠文档没用，必须集成到CI/CD流程中，让工具自动检查。）

7. 吞吐量改变了 PR 哲学：从小步快跑到飞速迭代

高吞吐量的 Agent 开发模式，彻底改变了对 Pull Request 的态度：

传统人工开发 Agent 开发
倾向大 PR，积累后再合并 拆小 PR，尽快合并
Review 周期长，阻塞少 Review 快，不因 Review 阻塞 Agent 效率
修复代价高，谨慎提交 出问题让 Agent 快速修复，不惧小错误

8. “Agent 生成”意味着什么：从代码到整个工程链路

在 OpenAI 内部，Agent 生成的内容已经不仅仅是业务代码，而是延伸到了工程链路的每个环节：

  1. 产品代码与测试
  2. CI 配置与发布工具
  3. 内部开发者工具
  4. 文档与设计历史
  5. 评估工具链
  6. 审查意见与回复记录
  7. 管理代码库本身的脚本
  8. 生产环境仪表板定义文件

人类工程师仍然在生产循环中，但不负责具体执行，而是专注于更高层次的工作：方案设计、架构设计、环境搭建。

9. 自主性水平的提升：从单任务到端到端流程

给定单个 Prompt，Agent 现在已经可以完成以下全套流程：

  1. 验证代码仓库当前状态
  2. 复现上报的 Bug
  3. 录制演示失败的视频
  4. 实现修复
  5. 驱动应用验证修复效果
  6. 录制演示修复结果的视频
  7. 开启 Pull Request
  8. 响应 Agent 和人类的反馈
  9. 检测并修复构建失败
  10. 仅在需要判断时才升级给人类
  11. 合并变更

10. 熵与垃圾回收：AI也会”学坏”

完全自主的 Agent 也引入了新问题：

Codex 会复制仓库中已有的模式——即便是那些不平衡或不够理想的模式。随着时间推移，这会导致不可避免的代码漂移。

仓库中原有的”垃圾代码”会成为 Agent 的错误参照，产生更多”垃圾”。解决方案：

  • 辅助函数集中化：优先使用共享工具包，而非各处手写 helper，保持不变量集中。
  • 边界校验：不做”YOLO 式”数据探测，依赖类型化 SDK，防止 Agent 基于猜测的数据结构构建逻辑。
  • 定期垃圾回收：设定一批后台 Codex 任务，定期扫描偏差、更新代码质量评分、开启针对性的重构 PR。

二、从理论到实践：我的思考与规划

读完整篇文章，我最大的感受是：OpenAI 不是在让人类适应 AI，而是在让整个工程环境变得对 AI 更友好。这或许才是未来软件工程的核心竞争力所在。

那么问题来了，我们自己的项目要怎么应用这些理念？

1. 四层基础设施：为Agent搭建友好环境

结合OpenAI的经验和我自己的实践，我认为为Agent搭建基础设施包含以下四个关键部分：

（1）项目工程品味规范

  • 明确的架构约束与代码风格规范
  • 通过自动化检查器强制执行
  • 错误信息要能直接指导Agent修复

（2）项目各个系统规范

  • 让 Agent 能够理解和访问各系统的接口与行为
  • 包括API文档、数据模型、权限系统等
  • 关键是要机器可读、可验证

（3）质量保障系统

  • 自动化测试、日志、指标
  • 让 Agent 具备自我验证能力
  • 集成到CI/CD流程中

（4）Agent 工作流程

  • 清晰的任务分解机制
  • PR 粒度控制策略
  • 反馈循环设计

2. 个人/小团队场景的可行性分析

在资源有限的个人或小团队项目中，直接照搬OpenAI的体系不太现实。但我们可以分阶段实施：

第一阶段：基础规范建设

  • 建立基本的代码规范（ESLint、Prettier等）
  • 编写关键模块的机器可读文档
  • 在CI中集成基础检查

第二阶段：增强Agent上下文

  • 创建项目知识库（架构决策记录、接口文档等）
  • 设计渐进式信息呈现机制
  • 让Agent能按需获取上下文

第三阶段：自动化工作流

  • 建立常见的自动化任务模板
  • 让Agent能自主执行测试、部署等操作
  • 设计有效的反馈循环机制

3. 实践案例：多Agent Code Review + Playwright自动化测试工作流

基于OpenAI的”Human steer, Agents execute”理念，我在最近的一个Web项目中尝试搭建了一个多Agent协作的代码审查和测试工作流。这个案例完整展示了如何将AI Agent融入实际开发流程。

3.1 背景与动机

项目是一个React + Node.js的全栈应用，传统开发模式下存在几个痛点：

  1. 代码审查效率低：团队Review周期长，容易成为瓶颈
  2. 测试覆盖不足：UI测试编写和维护成本高
  3. 反馈循环慢：从代码提交到发现问题时间跨度大

受到OpenAI文章的启发，我决定尝试构建一个多Agent协作系统，让不同的AI Agent分担不同职责，形成自动化工作流。

3.2 系统架构设计

整个系统由三个核心Agent组成，分工协作：

各Agent的职责定义：

（1）代码审查Agent

  • 基于项目代码规范和最佳实践审查代码
  • 检查潜在的性能、安全问题
  • 提出具体的改进建议和代码示例

（2）测试生成Agent

  • 分析代码变更影响的功能范围
  • 自动生成Playwright端到端测试用例
  • 确保关键用户流程得到测试覆盖

（3）测试执行Agent

  • 在隔离环境中执行Playwright测试
  • 捕获测试结果和失败截图
  • 生成详细的测试报告和问题复现步骤

3.5 效果评估与反思

取得的成效：

  • 审查效率提升：平均PR审查时间从2天缩短到2小时
  • 测试覆盖提升：UI测试覆盖率从30%提高到75%
  • 问题发现提前：80%的bug在代码提交阶段就被发现
  • 团队负担减轻：开发者可以更专注于功能实现，而非重复性审查

遇到的挑战：

  1. 上下文管理复杂度：不同Agent需要不同的上下文信息，需要精心设计文档结构
  2. Agent间协作难题：如何让Agent理解其他Agent的产出，形成有效协作链
  3. 测试稳定性问题：自动生成的测试有时过于脆弱，对UI微小变动敏感
  4. 误报率控制：初期Agent审查过于严格，产生大量无关紧要的建议

关键学习点：

  • 渐进式采用：不要试图一步到位，先从一个Agent、一个场景开始
  • 反馈循环设计：建立有效的反馈机制，让Agent能从错误中学习
  • 人类监督必不可少：完全自主的Agent仍不现实，关键节点需要人类把关
  • 可解释性很重要：Agent的决策过程需要透明，方便人类理解和信任

3.6 下一步优化方向

基于这个案例的经验，我计划进一步优化：

  1. Agent能力迭代：让Agent能从历史PR中学习团队偏好
  2. 动态上下文加载：根据任务类型动态加载最相关的上下文信息
  3. 测试用例维护：让Agent能识别和修复过时的测试用例
  4. 跨团队标准化：将这套工作流推广到更多项目团队

4. 基于现有工具的通用实践路径

除了上述具体案例，基于我使用 Claude Code、Cursor 等工具的经验，以下是一些通用可操作的步骤：

（1）优化Prompt工程

  • 为常见任务创建标准化Prompt模板（如”创建React组件”、”修复TypeScript错误”等）
  • 在项目中维护Prompt库，记录哪些Prompt效果好
  • 建立Prompt评估标准，持续迭代优化

（2）增强项目上下文

  • 在项目根目录添加CLAUDE.md或CONTEXT.md
  • 包含项目架构、技术栈、编码约定等关键信息
  • 让AI工具能快速理解项目背景和约束条件

（3）建立自动化检查点

  • 在关键节点（commit、PR、部署）添加AI辅助检查
  • 比如让AI自动生成测试用例、检查代码规范等
  • 逐步将人工检查转变为AI辅助检查

5. 风险与挑战：前进路上的坑

在实践过程中，我也遇到了一些挑战：

（1）上下文管理难题

  • 如何平衡上下文深度与广度？
  • 如何在有限的token内提供最有价值的信息？
  • 如何组织文档，让AI能快速找到所需信息？

（2）质量波动问题

  • AI生成代码的质量不稳定
  • 同样的Prompt，不同时间可能产生不同结果
  • 需要建立有效的质量评估机制

（3）团队协作障碍

  • 不同成员使用AI的方式不同
  • 如何统一团队的AI使用规范？
  • 如何让AI工具融入现有的协作流程？

6. 下一步行动计划

基于以上分析，我计划在接下来的项目中尝试以下措施：

  1. 完善项目文档体系

    • 重构现有文档，使其更加机器可读
    • 建立文档与代码的同步机制
    • 设计渐进式信息呈现结构

  2. 优化AI工具工作流

    • 为常用任务创建Prompt模板库
    • 在CI/CD中集成AI辅助检查
    • 建立AI生成代码的质量评估标准

  3. 探索自主性边界

    • 尝试让AI处理更复杂的端到端任务
    • 设计有效的监督和干预机制
    • 记录自主性提升带来的效率变化

总结：工程环境的”AI友好度”将成为新的竞争力

OpenAI的《Harness Engineering》向我们展示了一个未来图景：当AI成为工程团队的一等公民时，整个软件开发范式都会发生根本性改变。

对我们来说，重要的不是追赶OpenAI的技术水平，而是学习他们的工程思维：

  • 从”怎么用AI”转向”怎么为AI设计环境”
  • 从”人工检查”转向”系统化验证”
  • 从”文档给人看”转向”信息机器可读”

这条路还很长，但方向已经清晰：未来的软件工程，比拼的将不仅是编码能力，更是构建AI友好环境的能力。

后记：这篇文章是我阅读OpenAI《Harness Engineering》后的思考总结，结合了自己使用AI工具的一些实践经验。OpenAI的实践给了我很多启发，但具体到个人或小团队项目，还需要因地制宜地调整方案。
